== Overview and philosophy

`acdc` (AsciiDoc Tooling) is a spec-first (really, best effort) AsciiDoc parser and toolchain built in Rust.
The project aims to be a potential canonical implementation of the https://gitlab.eclipse.org/eclipse/asciidoc-lang/asciidoc-lang[AsciiDoc Language specification] once it is formalized.

The toolchain includes a parser library, converters for various output formats (HTML, manpage, Markdown, terminal), a linting support crate, a command-line interface, and a Language Server Protocol (LSP) implementation for editor integration.

=== What I'm trying to build

I want to create a parser that follows the AsciiDoc Language specification whenever it's been formalized.
Think of this as a reference implementation that tracks the evolving spec.
When the spec is undefined or ambiguous, I match Asciidoctor's behavior to keep things familiar for users.

The goal is to eventually be the canonical implementation - the one people point to when they want to understand how the spec should work in practice.
Along the way, I'll be feeding implementation experience back to the spec process.

=== How I'm approaching this

I'm taking a simple, pragmatic approach:

. When the spec has made a formal decision, that's what I implement - no questions asked
. Where the spec is still undefined, I match what Asciidoctor does
. I document any deviations (especially where following the spec means diverging from Asciidoctor)
. I check correctness and compatibility first, and measure performance changes against an unchanged baseline

I want familiar Asciidoctor behavior where it fits the parser's structured model.
Documented differences and remaining specification work mean this is not a claim of complete conformance.

== Why PEG?

I chose Parsing Expression Grammars (PEG) for the parser because that's what the AsciiDoc Language folks decided on in https://gitlab.eclipse.org/eclipse/asciidoc-lang/asciidoc-lang/-/blob/main/spec/sdrs/sdr-004-use-peg-for-formal-grammar.adoc[SDR-004: Use PEG for Formal Grammar].

**The grammar can express the specification's rules directly**.
The implementation also handles compatibility, recovery, and source tracking, so it does not map one-to-one to every draft rule.

**Debugging is straightforward**.
Named rules and tracing help locate the boundary that accepted or rejected input.

**It's readable**.
PEG grammars read almost like pseudocode from the spec.
Compare that to hand-written recursive descent parsers or complex parser combinator chains, and it's a clear win for maintainability.

**Implementation**.
I'm using https://github.com/kevinmehall/rust-peg[rust-peg], which generates efficient parsers from PEG grammar definitions embedded right in the Rust source.

=== The trade-offs

PEG parser generation adds compile time, and backtracking can add runtime work.
The parser already has performance work for allocation, attributes, source mapping, and verbatim content.
I use focused checks while editing and paired benchmark runs before claiming a speed improvement.

== Three-stage processing pipeline

The toolchain works in three stages:

[source]
----
Input Document → [Preprocessor] → [Parser] → [Converter] → Output
----

=== Stage 1: preprocessor

The preprocessor (`acdc-parser/src/preprocessor/`) handles text-level transformations that need to happen before parsing. This includes:

* Expanding `include::[]` directives (recursively processing included files)
* Evaluating conditional directives like `ifdef::[]`, `ifndef::[]`, and `ifeval::[]`
* Processing document attribute definitions (`:attr:`) and multi-line attribute continuations

Why keep this separate?
Because the AsciiDoc spec says these expansions must happen before parsing.
The preprocessor works on raw text and produces expanded content that the parser then processes.

=== Stage 2: parser (PEG + inline preprocessing)

This is where the actual parsing happens (`acdc-parser/src/grammar/`).
The preprocessed text gets transformed into an Abstract Syntax Tree (AST).

==== Main document grammar

The primary PEG grammar lives in `document.rs` using the `peg::parser!` macro.
It handles document structure (header, sections, blocks), block-level elements (paragraphs, lists, tables, delimited blocks), attributes and metadata, and all the nesting rules.

==== Inline preprocessing

Inline content needs special handling, as specified in https://gitlab.eclipse.org/eclipse/asciidoc-lang/asciidoc-lang/-/blob/main/spec/sdrs/sdr-005-formal-grammar-for-inline-syntax.adoc[SDR-005: Formal Grammar for Inline Syntax].

SDR-5 replaces output-dependent substitutions with a formal inline grammar.
Attribute references and passthrough boundaries need preprocessing before that grammar runs.

I use a two-pass approach:

. **Preprocessing pass**: Expand attribute references and protect passthrough regions, retaining their source locations
. **Parsing pass**: Parse the resulting source into `InlineNode` elements and restore protected content

Converters then render those nodes and escape text as required by their output format.
The existing `pre-spec-subs` compatibility feature retains some legacy ordered behavior; this is not a claim of complete SDR-5 conformance.

==== Parsing and conversion boundary

The project follows SDR-5's decision to keep parsing independent of conversion.
The parser must not generate HTML tags, PDF markup, or roff commands to determine an attribute value or evaluate a conditional.
Explicit checks of intrinsic attributes such as `backend` remain valid; they are author-supplied conditions, rather than an effect of rendering attribute content.

Formatted document attributes retain AsciiDoc source text and private inline parsing profiles.
For example, `:value: pass:q[*Bold*]` exposes `*Bold*` through text reads, JSON, conditions, and include paths, while a reference produces bold inline content through its quote profile.
Text reads never expose `<strong>Bold</strong>` or backend-specific equivalents for this value.
This deliberately differs from Asciidoctor, which converts such values during assignment.
See https://docs.asciidoctor.org/asciidoc/latest/attributes/attribute-entry-substitutions/[Asciidoctor's attribute-entry documentation].

SDR-5 leaves the mapping of custom `pass:` substitution lists open for further research.
Supporting common lists through parsing profiles is an acdc policy; it is not an exact rule prescribed by that design record.
Common profiles support quotes (`q`), macros (`m`), replacements (`r`), post replacements (`p`), and `normal`, including long names and combinations.
Attribute references selected by `a` freeze at definition time, before the retained profile runs at use; both `a,q` and `q,a` therefore parse the frozen source.
Aliases preserve profiles and protect raw fragments.
An explicit `a` list imports referenced profiles and protects its surrounding source; an explicit structural list applies its own rules to the complete expanded source.
Unused definitions register no footnotes, index terms, or anchors.
Anonymous footnotes register separately at each use; named footnotes retain the existing shared-ID policy.

Orders that require generated output to be escaped again, such as `q,c` and `m,c`, stay literal with a structured parser warning.
Text-only lists combining `a` and `c` also stay literal with a warning when their references carry inline profiles; their effect on those profiles needs a separate design.
Unknown substitution names stay literal with a warning.
These restrictions apply to attribute-entry values; the existing inline passthrough and block-substitution behavior is separate.
Profiles apply typography during conversion, including raw text, code, and backtick spans.
Their escaped replacement patterns remain literal and do not undergo surrounding block replacements a second time.
For example, `:value: pass:r[\(C)]` exposes `\(C)` through text reads and renders `(C)` at each use.
Asciidoctor removes this escape during assignment, so ordinary prose and replacements-enabled code can later render `©`.
This difference follows acdc's source-first policy under SDR-5; SDR-5 does not prescribe these custom-list semantics.
Passthrough source arrows follow the profile order: `pass:c,r[->]` renders an arrow, whereas `pass:r,c[->]` and `pass:r[->]` retain the source characters.
Ordinary blocks deliberately recognize source arrows whenever replacements are enabled, even without special-character escaping; Asciidoctor requires the escaped angle-bracket form.
Both decisions are converter compatibility policies, not requirements of SDR-5.

The implementation stores source spans and compact rule lists rather than converted markup or owned inline trees.
Profiles are parsed when referenced in document content, so one parsed document can be converted to several formats.
Earlier text-only attribute escaping and ordinary quotes-before-attributes ordering remain compatibility policies.
For example, `:value: <x>` still exposes `&lt;x&gt;` through attribute text reads, and `:value: *Bold*` displays literal asterisks under normal substitutions.
These policies match Asciidoctor but do not implement SDR-5's proposed late escaping and attribute-before-grammar semantics.
Changing them would affect public value reads, conditions, include paths and document rendering, so they require a separate migration decision.
Backend-neutral attribute expansion, source locations, and caller assignment policy remain necessary before includes and conditions can be processed.

==== Attribute parsing: blocks vs inlines

Formatting spans support a smaller attribute list than block elements.
Inline macros have their own rules: links and cross-references can also have named attributes.

The comparison below applies to formatting spans such as `[.role]*text*`, not to every inline node.

Here's the comparison:

[cols="1,2,2",options="header"]
|===
|Attribute |Formatting spans |Block elements

|**Roles**
|Multiple (space-separated) +
`[.role1.role2]*text*` → `class="role1 role2"`
|Multiple (vector) +
`[.role1.role2]` → separate borrowed roles

|**ID**
|Single +
`[#myid]*text*` → stored as `Option<&str>`
|Single +
`[#myid]` → stored as `Option<Anchor>`*

|**Options**
|❌ Not supported +
`%` treated as literal character
|✅ Multiple +
`[%option1%option2]` → separate borrowed options

|**Style**
|❌ Not supported
|✅ Single +
`[style]` → `Option<&str>`

|**Named attrs**
|❌ Not supported
|✅ Multiple +
`[key=value,foo=bar]` → `ElementAttributes`

|**Positional attrs**
|❌ Not supported
|✅ Multiple +
`[pos1,pos2,pos3]` → read with `BlockMetadata::positional_attributes()`

|**Anchors**
|❌ Not supported
|✅ Multiple +
`[[anchor1]][[anchor2]]` → `Vec<Anchor>`
|===

**The percent character quirk**.
In inline contexts, `%` is a literal character, not an option separator like it is in block contexts.
This means `[.role%option]*text*` becomes `class="role%option"`, with the percent sign included in the role name.
If you start with a percent like `[%option]*text*`, that entire thing becomes the role name: `class="%option"`.

**Role storage**.
Both contexts support multiple roles, but they store them differently.
Inline elements join multiple roles into a single space-separated string (`"role1 role2"`), while block metadata keeps them as separate vector items.
This is an implementation detail - the HTML output is the same either way.

==== State tracking

The parser keeps track of state through `ParserState`, which includes document attributes (key-value pairs from `:name: value` syntax), a footnote tracker for collecting footnotes, a TOC tracker that builds table of contents entries from section headers, and various options like safe mode and timing flags.

==== Location tracking

Parsed nodes carry source locations.
`LineMap` maps offsets to line and column positions; source remapping accounts for preprocessing and included files.
Programmatically constructed nodes can carry caller-supplied or default locations.

=== Stage 3: converters

Converters (`converters/`) transform the AST into various output formats.
They implement the `Processable` trait in link:converters/core/src/lib.rs[`converters/core`].
The trait owns converter setup and conversion; parser options are validated before parsing.

The converters are:

. HTML (`converters/html`) for HTML5 output with semantic markup and accessibility attributes. Also ships a `html5s` variant (inspired by https://github.com/jirutka/asciidoctor-html5s[Jakub Jirutka's asciidoctor-html5s]) that emits `<section>`/`<aside>`/`<figure>` instead of div-based layout
. Manpage (`converters/manpage`) for native roff/troff output suitable for the `man` command
. Markdown (`converters/markdown`) for CommonMark and GitHub Flavored Markdown output
. PDF (`converters/pdf`) through the Rust Typst engine
. Terminal (`converters/terminal`) for ANSI-formatted terminal display

Why this trait-based design?
I didn't think it over too much, honestly.
It keeps things clean - the parser doesn't know anything about output formats.
Each converter defines its own options and error types, which gives type safety.
And implementing the trait to add a new output format is straightforward.

==== Document attribute layering

Application overrides supplied through `with_attribute()` or `with_attributes()` normally take precedence over document entries.
Use `with_default_attribute()` or `with_defaults()` for values the document can replace.
The CLI passes `-a` inputs through the same parser policy, including soft assignments.
Read-only and API-only names remain protected.
Some attributes have explicit exceptions: a caller-set `sectnums` can change in the body, but a caller-requested unset remains locked.

`Document::attributes` contains the effective end-of-header values.
Accepted body assignments become ordered `Block::DocumentAttribute` events.
Converters use `TraversalContext` to apply those events and restore parent values after a nested AsciiDoc table cell.
The parser owns assignment policy; converters choose their defaults and output behavior.

`toclevels` and `sectnumlevels` need not exist as attributes for their consumers to use default depths of 2 and 3.
`outdir` and `outfile` are conversion-result metadata, not attributes available during parsing.

==== Type-based AST instead of property-based

One thing worth calling out: the spec's reference implementation uses a property-based approach for the AST (look at the `*.json` fixtures in `acdc-parser/fixtures/tests/`). Everything is a generic object with properties like `"name"`, `"type"`, `"variant"`, etc.

I went a different route.
I created distinct Rust types for each element - `Block`, `InlineNode`, `Paragraph`, `Section`, and so on.
Instead of having a generic node with a `type` property, I have proper enum variants and structs.

Why?
Because it lets me leverage Rust's type system as much as possible.
The compiler catches mistakes at compile time instead of runtime.
Enum variants make the supported element kinds explicit.
Public AST types marked `#[non_exhaustive]` let later versions add fields or variants; external callers must allow for those additions.
And converters get better ergonomics because they can destructure specific types rather than checking string properties.

The trade-off is that my AST structure doesn't map one-to-one with the spec's JSON representation.
Serialization provides the ASG representation used by the `tck` command.
Producing that representation does not by itself establish specification conformance.

== Key design decisions

=== Errors and recovery

Parsing returns `Result<ParseResult, Error>`.
Fatal input, decoding, resource-limit, and grammar errors stop the parse.
Recoverable problems, such as an unreadable include or an unterminated block, can retain a document and add located warnings.

Callers read all warnings through `ParseResult::warnings()`.
`source_recovery()` reports the first warning that affects source content or structure, even after `take_warnings()` moves the warning list.
Applications that require complete input must check recovery before acting on the parsed document.
Strict mode rejects malformed manpage titles; it does not turn every warning into an error.

=== Module organization

The workspace is organized into clearly bounded modules:

[source]
----
acdc/
├── acdc-cli/          # Command-line interface
├── acdc-editor-wasm/  # WASM live editor (syntax highlight + HTML preview)
├── acdc-lint/         # Lint command support and lint registry
├── acdc-lsp/          # Language Server Protocol implementation
├── acdc-parser/       # Parser library (PEG grammar, preprocessor, AST)
└── converters/
    ├── core/          # Shared converter infrastructure (Processable, Visitor traits)
    ├── dev/           # Development utilities (unpublished)
    ├── html/          # HTML5 output (standard + html5s semantic variant)
    ├── manpage/       # Native roff/troff manpage output
    ├── markdown/      # CommonMark / GitHub Flavored Markdown output
    └── terminal/      # ANSI terminal output
----

This keeps clear boundaries - parser, CLI, linting, LSP, and converters are independently testable.
The parser has no knowledge of output formats or lint policy for the most part.
An exception to this perhaps is warning on unsupported counters, which it does.
Converters, linting, and the LSP depend on the parser, not the other way around.
New features can be scoped to specific modules without touching everything else.

=== Location tracking

Every AST node includes location information:

[source,rust]
----
pub struct Location {
    pub absolute_start: usize,
    pub absolute_end: usize,
    pub start: Position,
    pub end: Position,
}
----

Each `Position` carries a `u32` line and column plus an optional include chain.
After parsing, line and column refer to the original source; start and end can belong to different files.
Byte offsets normally refer to those original files, with an inclusive end.
Reindented includes retain preprocessed byte offsets, so use their original line and column for navigation.
`Location::byte_len()` returns `None` across files.
`ParseResult::source_location()` resolves a location to its source file and anchors a cross-file span at its start.

== Extension points

=== Adding new converters

If you want to add a new converter, implement the `Processable` trait. The trait requires:

* `document_attributes_defaults()` - Provide converter-specific default attributes (optional override)
* `new()` - Initialize the converter with its options and a parser options builder
* `convert()` - Convert a parsed document, writing output to the destination
* `document_attributes()` - Access the document attributes

The best way to understand how this works is to look at an existing converter.
The Terminal converter (`converters/terminal/src/lib.rs`) is a good starting point - it's relatively straightforward and shows all the essential patterns.

To add a new converter:

. Create a new crate under `converters/`
. Add dependencies on `acdc-converters-core` and `acdc-parser`
. Define your options and error types
. Implement the `Processable` trait
. Walk the AST to generate your output format

=== Adding new grammar rules

To extend the parser with new AsciiDoc constructs:

. Check the draft specification and compare the source with Asciidoctor before choosing behavior.
. Add a focused source fixture and review its expected AST through the parser fixture workflow.
. Add the model type in `acdc-parser/src/model/`, with source locations and serialization where needed.
. Add the grammar rule and include the node in block or inline traversal and location remapping.
. Update affected converters, diagnostics, and documentation. Run focused checks before the workspace validation boundary.

=== Adding new block or inline types

For block-level elements: add a variant to the `Block` enum in `acdc-parser/src/model/mod.rs`, implement the parsing rule in the grammar, and add converter support in each backend.

For inline elements: add a variant to the `InlineNode` enum in `acdc-parser/src/model/inlines/mod.rs`, figure out if inline preprocessing is needed (check SDR-005), implement the parsing rule in the inline grammar, update location mapping if needed, and add converter support.

== Index terms and callouts

=== Index terms

The parser supports AsciiDoc index terms in both visible and concealed forms:

* **Flow terms** - Visible in text: `((term))` or `indexterm2:[term]`
* **Concealed terms** - Hidden from output: `\(((primary,secondary,tertiary)))` or `\indexterm:[primary,secondary,tertiary]`

`IndexTermKind` stores inline-node labels; concealed terms can have up to three levels, while flow terms have one.
`IndexTermRelationship` represents `see` and `see also` targets.
Catalog labels retain their registration-time text separately from later display substitutions.
HTML index catalog generation is an acdc extension enabled with `:acdc-index:`; `[index]` alone does not enable it.

=== Callout references

Callout markers in verbatim blocks (`<1>`, `<2>`, or auto-numbering `<.>`) are parsed as `CalloutRef` with explicit or auto-numbered kinds.
The parser resolves auto-numbered markers to their actual numbers during parsing.

== Future directions

=== Parallel parsing

I'm planning to look into parallel processing of files.
If we need to parse and convert hundreds of files, I'd like to not take hundreds x "time that takes one".

=== Performance optimization

Performance work continues alongside compatibility fixes.
I measure runtime and allocation changes with paired runs and an unchanged control, because machine drift can hide small differences.
Compile time and grammar size remain separate concerns.

=== Incremental parsing for the LSP

Today the LSP reparses the whole document on every change.
Incremental parsing would cut latency on large files, but it requires grammar-level support that PEG doesn't give us for free - this is a longer-term research item.

== Spec compliance and compatibility

=== Following the spec

I'm following the AsciiDoc Language specification wherever it's been formalized.
When there's a formal spec decision, that's what I implement - it's the primary source of truth.
I reference the relevant Specification Document Requirement (SDRs) in the implementation, and I'm feeding implementation experience back to the spec process, which in all truth I haven't been great at doing with the frequency I want.

The test suite includes spec compliance tests via the `tck` command.

=== Asciidoctor compatibility

Where the spec is undefined or ambiguous, I match Asciidoctor behavior to keep things familiar for users.
I document any deviations in code comments and tests, and I'm tracking spec evolution to update the implementation when things get formalized.
Building a compatibility matrix is future work.

=== Testing

The `tck` command produces ASG output for the AsciiDoc Language TCK harness.
The selected TCK tests, parser JSON fixtures, converter fixtures, integration tests, and property tests cover different contracts.
A passing fixture only proves agreement with its expected output; compatibility changes also need direct reference checks.
See the repository and parser `AGENTS.md` files for feature coverage, fixture approval, and validation commands.

== Contributing

This architecture isn't set in stone.
As the project evolves, feel free to propose changes via issues or pull requests.
Just document your decisions with rationale, consider spec alignment before making big architectural changes, and try to maintain extension points for future flexibility.
