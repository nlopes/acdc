= Inline parsing

The inline parser builds a tree of text, formatting, and macro nodes.
It keeps source locations so consumers can find the original text after attribute expansion and include processing.
The public entry point for inline fragments is `acdc_parser::parse_inline`; full-document parsing supplies the attributes active at each block.

== Parsing and conversion

The design uses https://gitlab.eclipse.org/eclipse/asciidoc-lang/asciidoc-lang/-/blob/main/spec/sdrs/sdr-005-formal-grammar-for-inline-syntax.adoc[SDR-5] as a reference for separating parsing from conversion.
The parser creates inline structure; converters render it and apply output escaping.
The default-on `pre-spec-subs` feature also supports experimental ordered substitutions for compatibility with Asciidoctor.
This is not a claim of complete SDR-5 conformance.

Two stages share the work:

. `inline_preprocessor.rs` identifies protected passthrough regions, expands enabled attribute references, and records how transformed text maps to the source.
. `inlines.rs` parses that text into `InlineNode` values. The processing helpers restore protected content and remap the resulting locations.

Substitution order still matters.
Normal content processes quotes before attributes, so an attribute value cannot create or remove earlier formatting boundaries.
An explicit `subs="attributes,quotes"` list lets expanded values affect later formatting.
See link:../../README.md#parsing-and-conversion[the parser README] for the supported profiles and deliberate differences.

== Inline structure

Formatting nodes can contain other inline nodes.
Links, cross-references, footnotes, and visible index terms can also contain inline labels.
Keep these labels nested; do not flatten them into generated markup and parse that markup again.
Unmatched formatting marks normally remain plain text.
Malformed or incomplete macros follow their own literal-text or recovery rules.

When changing recognition, keep the grammar's lookahead and parsing rules consistent.
A lookahead that accepts a different delimiter boundary can split a paragraph before the real parser reaches it.

== Document attributes

Document attribute entries resolve references against the values available when the entry is defined.
Later body entries affect later content, while `Document::attributes` remains the end-of-header snapshot.
Accepted body changes appear as ordered set/unset events.

Text reads preserve the attribute's AsciiDoc representation, not converted HTML or another output format.
Supported whole-value `pass:` profiles retain their parsing behavior when the value is used.
Unused values must not register footnotes, anchors, or index entries.

An unresolved ordinary attribute reference remains literal.
Escaped references bypass lookup and lose the applicable escape only when attribute substitution is enabled.
Counter references are unsupported: they warn and are removed when attribute substitution is active.
Do not interpret a missing value, an explicit unset, a presence value, and an empty text value as the same state.

== Passthroughs

Single and double plus forms protect text from ordinary inline parsing and retain special-character escaping for output.
Triple plus and an empty `pass:` profile retain raw content.
A named `pass:` profile applies its enabled substitutions in order.
The inline `verbatim` group does not include block callouts.

Protected content is represented internally until it can be restored in the inline tree.
The placeholder bytes and offsets are private implementation details.
They must never appear in public text, labels, attributes, diagnostics, or serialized output.
When passthrough recognition is disabled, its literal syntax still follows the surrounding enabled substitutions.

== Source locations

Track transformed and original coordinates separately.
Attribute values can have a different length from their references, and passthrough placeholders do not have the same length as their source.
Use the location-mapping helpers instead of adding transformed offsets to source positions.

After full-document parsing, each location boundary identifies its original line, column, and include chain.
A location can start and end in different files.
Byte offsets normally refer to the original source; reindented includes retain preprocessed byte offsets, so their original line and column must be used for navigation.
Do not assume that slicing `ParseResult::source()` with an AST location recovers the original text.

Regression cases should cover nested formatting, Unicode, escaped delimiters, attribute expansion, and included input when those paths are affected.
Use the fixture and validation workflow in link:../../AGENTS.md[the parser developer guide].
